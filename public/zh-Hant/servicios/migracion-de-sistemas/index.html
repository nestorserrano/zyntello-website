解決什麼問題

舊系統一直留著，是因為沒人敢動它

還在用一套沒人維護的系統的公司，幾乎都不是心甘情願：而是因為遷移代表要拿多年的歷史資料冒險、開立發票要停擺幾天，事後還可能發現餘額對不上。這種擔心很合理，而解決它靠的是方法，不是膽量。

  • 原廠已經不再支援這個版本
  • 跑系統的那台伺服器，早就超齡服役了
  • 沒人說得清資料庫裡到底有什麼
  • 歷史資料散落在系統和好幾個 Excel 裡
  • 上一次遷移留下的餘額，一直沒對平過
  • 開立發票停擺幾天，根本不可能

包含什麼

具體給到你什麼

先摸清來源系統，再動手搬

來源系統的資料表、欄位、代碼和規則，全部寫成文件。從 Aspel 遷移到 Profit 時我們就是這麼做的：先研究資料庫，再去碰它。

在副本上完整演練

整個遷移在一份副本上完整跑過，需要幾遍就跑幾遍。演練乾乾淨淨通過了，才去動正式環境。

遷移前後都要對平

客戶、供應商、庫存與會計的餘額，在兩套系統裡各量一遍。對不平，遷移就還沒結束。

營運不中斷

切換安排在月結或週末，期間舊系統仍可查詢。

順手把資料清乾淨

重複的客戶、沒有異動的品項、孤立的代碼，在遷移時就清理掉，而不是事後再說。把垃圾一起搬過去，等於為它付兩次錢。

基礎設施也能遷移

從自有伺服器到雲端，或從老舊的 SQL Server 換到仍有支援的版本，開工前就把回復計畫寫好。

如何運作

三步完成

  1. 盤點來源系統

    有哪些資料、狀態如何、目標系統需要哪些。

  2. 演練與對平

    在副本上做完整遷移，直到餘額一致。

  3. 切換與陪跑

    在約定的時段正式遷移，並在頭幾次結帳時提供支援。

細節之處

每天用起來才感受得到的地方

遷移需要的，而不是全部

有時比較好的做法是遷移餘額加上幾年的明細，更早的放進一個唯讀的查詢檔。這要和會計一起決定，不能圖技術上方便。

主檔先行

客戶、供應商、品項和會計科目表，要比交易異動先遷移。一筆異動掛在遷移錯誤的主檔上，錯誤就會帶進每一張報表。

舊系統不在第一天關掉

在約定的一段期間內保持唯讀查詢。這是任何遷移最便宜的保險。

每條轉換規則都寫下來

哪個代碼變成了哪個，為什麼。一年後總會有人問某筆餘額是從哪來的，到時候必須答得出來。

讓使用者拿自己的數字來驗證

應收帳款部門核對自己的帳款，倉儲核對自己的庫存。最熟悉資料的人，最能看出哪裡對不上。

有回復計畫

如果切換失敗，清清楚楚知道怎麼退回舊系統、要花多少時間。沒有這份計畫，就不開工。

常見疑問

常見問題

要停多久？

通常上班時間完全不用停：切換安排在約定的時段，例如月結或週末。

歷史資料會遺失嗎？

不會。要嘛全部遷移，要嘛某個日期之前的放進唯讀查詢檔。這件事事先和會計一起決定。

你們能從哪些系統遷移？

我們做過從 Aspel 到 Profit、以及 Profit 各版本之間的遷移，也做 Softland 和 ODOO。只要你的系統把資料存在一個可存取的資料庫裡，就能摸清它的結構。

來源資料很髒怎麼辦？

幾乎都是髒的。清理本來就是遷移的一部分：重複資料、孤立代碼和對不平的餘額，都在切換前解決。

我怎麼知道遷移成功了？

因為兩套系統裡量出來的餘額一致，而且由每天使用這些資料的人親自驗證過。

伺服器也能遷移嗎？

可以：從自有伺服器移到雲端，或移到仍有支援的 SQL Server 版本，回復計畫事先寫好。
